# 브라우저 기반 상시 CTF 풀이기: 근거와 설계 제안

작성: 2026-10-08 · 상태: 연구 및 설계 제안, 라이브 경로 초기 구현 중

## 1. 목표와 조사 범위

사용자가 CTF 사이트 URL과 자기 계정 접근 수단을 주면 **기존 Codex 실행 환경**이 브라우저를 열어 로그인하고, 문제를 발견하고, 풀고, 플래그를 제출하고, 사이트의 판정을 확인한 뒤 다음 문제로 넘어간다. 사이트별 API 연결기나 사전 지원 플랫폼 목록을 시작 조건으로 두지 않는다. 최신 사용자 지침에 따라 chrome-use와 연결된 Chrome 프로필을 우선하고, Codex 내장 chrome 플러그인은 최종 호환성 대안으로만 둔다. RTK, context-mode, MCP, intent-gate는 이미 설정된 것을 목적에 맞게 사용한다.

이번 조사는 Exa 검색 14회로 CTF 에이전트·실제 대회 평가·브라우저 에이전트·장기 문맥·프롬프트 주입·Codex 런타임·공개 구현을 찾고, 관련 원문/공식 문서/저장소 페이지 30개를 직접 열어 비교했다. 그중 내용 없는 페이지 1개는 근거에서 제외했다. 주요 GitHub 저장소는 README에 그치지 않고 특정 커밋의 구현 파일과 아키텍처 문서를 확인했다. 아래 수치는 각 논문의 시험 환경에서만 성립한다. 이 목록은 높은 관련성의 공개 자료를 추린 것이며 모든 공개 논문의 완전한 목록이라는 뜻은 아니다.

## 2. 현재 코드와 제품 목표의 간격

| 현재 확인된 동작 | 제품 목표에 필요한 변경 |
|---|---|
| `LocalTaskSource`는 `task.json`/`evaluator.json`/`public` 디렉터리에서 문제 하나를 읽는다. [`task_source.py`](../../src/ctfh_core/task_source.py) | 브라우저가 대회 문제 목록을 탐색하고 URL·제목·카테고리·상태·첨부파일을 발견해야 한다. |
| CLI `smoke`는 로컬 fixture 한 문제를 한 번 실행한다. [`cli.py`](../../src/ctfh_core/cli.py) | 대회 전체를 계속 순회하고, 새 문제와 중단된 문제를 재개해야 한다. |
| Codex 실행은 격리 설정에서 `memories=false`, `hooks=false`, `plugins=false`를 지정하고 `codex exec --ephemeral`을 쓴다. [`agent.py`](../../src/ctfh_core/agent.py) | 실제 실행에는 사용자의 신뢰된 Codex 설정과 MCP를 읽고, 지속 가능한 thread ID를 저장해야 한다. 현재 경로는 비교 실험용으로 유지할 수 있다. |
| 브라우저와 기본 설정은 시도 단위로 격리된다. [`environment.py`](../../src/ctfh_core/environment.py) | **대회 단위** 브라우저 로그인 상태와 **문제 단위** 작업 공간의 수명을 분리해야 한다. |
| 기존 OutcomeAuthority는 로컬 evaluator를 판정한다. | 실제 대회의 정답 판정은 제출 뒤 새로 관찰한 사이트 응답/점수판이 결정해야 한다. |

기존 V3 커널, 아티팩트 저장, 격리 작업 공간, 오프라인 평가 코드는 버릴 필요가 없다. 다만 현재 `smoke`와 격리 프로필을 상시 풀이기의 시작 경로로 그대로 재사용하면 사용자가 붙여 놓은 MCP·브라우저 인증·Codex 대화 이력이 사라진다. 이는 [`DECISIONS.md`](../DECISIONS.md)에 기록된 2026-10-08 제품 목표와도 맞지 않는다.

## 6. Codex 네이티브 실행 경로

공식 [Codex App Server 문서](https://developers.openai.com/codex/app-server.md)는 `thread/start`/`thread/resume`, `turn/start`, 이벤트 스트림, `thread/list`를 제공한다. [비대화형 CLI 문서](https://developers.openai.com/codex/noninteractive)는 `codex exec --json`, 세션 ID로 `exec resume`, 그리고 `--ephemeral`이면 세션 기록을 남기지 않는다고 설명한다. [설정 문서](https://developers.openai.com/codex/config-basic)와 [MCP 문서](https://developers.openai.com/codex/mcp)에 따르면 Codex의 사용자 설정은 `config.toml`에 있고 MCP 구성도 그 설정에 둔다. 로컬 `codex 0.161.0`은 app-server와 exec-resume 명령을 노출한다.

**권장 경로:** 하나의 얇은 대회 컨트롤러가 신뢰된 사용자 환경의 `codex app-server`를 구동하고 공식 thread/turn 이벤트를 소비한다. 대회 컨트롤러는 브라우저를 별도 에이전트로 흉내 내지 않고, Codex가 기존 chrome-use 도구를 사용하도록 한다. 시작 시 실제 MCP 도구 목록·인증·스킬/RTK 가용성을 확인한다. 사용자 설정을 통째로 샌드박스에 복사하지 않는다. 이 런타임은 현재 benchmark용 `--ephemeral` 경로와 별개 프로필이다.

`codex exec resume --json`은 더 작은 CLI 시제품 대안이다. 최초 구현에서 app-server 통합 비용이 큰 경우 같은 상태 원장/브라우저 수명 규칙을 유지하면서 이 경로로 검증할 수 있다. 장시간 실행, 진행 중 이벤트, 스레드 목록 조회와 재연결에는 app-server가 더 적합하다는 것이 현재 설계 판단이다. 브라우저 MCP 연결이 app-server에서 현재 사용자 프로필 그대로 보이는지는 실제 실행 테스트로 확인해야 한다.

## 7. 제안 구조와 수명

```text
사용자: CTF URL + 계정 접근 수단 + 실행 범위
                    │
                    ▼
        대회 컨트롤러 / SQLite 상태 원장
          │         │              │
          │         │              └─ 제출 원장·재시작 복구·작업 우선순위
          │         ▼
          │   Codex app-server (사용자 신뢰 설정/MCP)
          │       ├─ 대회 탐색 스레드
          │       └─ 문제별 풀이 스레드 + 격리 작업 공간/터미널
          ▼
  대회 단위 인증 브라우저 세션
chrome-use / 연결된 Chrome 프로필 → 내장 chrome 최종 대안
          │
          └─ UI에서 문제 발견·자료 받기·제출·새 화면으로 판정 확인
```

수명/권한을 다음처럼 나눈다.

1. **대회:** URL/origin, 계정 식별자, 브라우저 소유자/프로필, 전체 상태 원장. 브라우저 로그인은 대회가 끝나거나 사용자가 종료할 때까지 보존한다. 브라우저 제어는 한 소유자가 직렬화한다.
2. **문제:** 사이트에서 관찰한 식별자/URL/제목/분류/상태, 문제별 Codex thread ID, 작업 공간, 첨부파일, 마지막 인계 요약. 다른 문제의 오염된 페이지 텍스트를 자동으로 넘기지 않는다.
3. **시도:** 사용한 모델/도구/환경, 명령·파일·도구 관찰의 증거 참조, 확인된 사실, 실패한 가설, 다음 행동. 독립 실험 시도는 V3 격리 실행기를 이용할 수 있다.
4. **제출:** 문제·후보 플래그 해시·제출 시각·브라우저 관찰 증거·판정. `SUBMITTING`을 먼저 기록하고 클릭 후 새 화면을 읽어 `ACCEPTED`, `REJECTED`, `UNKNOWN` 중 하나로 확정한다. `UNKNOWN`은 점수판/문제 상태를 재조회한 뒤 처리해 중복 제출을 막는다. 실제 플래그/계정 비밀은 일반 로그에 넣지 않는다.

문제 상태는 `DISCOVERED → CLAIMED → SOLVING → CANDIDATE → SUBMITTING → ACCEPTED|REJECTED|UNKNOWN`으로 시작한다. 시간/예산 제한이나 막힌 문제는 `PARKED`로 두고 재시도 근거와 다음 점검 시점을 남긴다. 문제 목록은 주기적으로 브라우저에서 재방문해 새 문제/상태 변화를 발견한다. 이 재방문은 명시된 사이트와 문제가 가리키는 범위 안에서 수행한다.

### 한 바퀴의 동작

1. URL로 브라우저를 열고 현재 로그인 여부를 확인한다. 필요하면 계정 접근 수단으로 로그인한다. 추가 인증이 필요한 때만 사용자 인계 상태로 멈추고, 완료 후 같은 대회 상태로 재개한다.
2. Codex가 문제 목록을 브라우저로 읽는다. 각 항목은 URL/사이트 내 ID가 있으면 그것을 우선 키로 쓰고, 없으면 사이트+관찰한 식별 정보로 임시 키를 만든다. 탐색/선택/제출마다 새 브라우저 관찰을 받아 오래된 DOM을 근거로 클릭하지 않는다.
3. 풀이자는 문제 설명·첨부파일·대상 정보를 읽고 문제별 격리 공간에서 셸, 네트워크 도구, 소스 분석, 브라우저 등을 사용한다. 도구 출력이 길 때 RTK/context-mode를 선택해서 축약하되, 필요한 원본 증거의 위치를 보존한다.
4. 후보 플래그가 생기면 제출 원장에 먼저 기록하고, 사이트 UI로 제출한다. 판정은 Codex의 추측이나 문자열 형식이 아니라 사이트의 새 응답/점수판 변화에서 확인한다.
5. 정답이면 문제를 닫고 다음 문제로, 오답이면 동일 후보 중복을 막고 풀이를 계속한다. 판정 불명/세션 종료면 브라우저 상태를 재동기화한다. 작업이 중단되면 SQLite 상태 + Codex thread ID + 인계 기록으로 같은 문제부터 재개한다.

intent-gate에는 제품 목표와 승인 범위를 유지하고, Codex thread에는 풀이 대화의 연속성을 유지하며, SQLite에는 대회의 **관찰 가능한 진행 상태**를 둔다. 셋 중 하나가 다른 둘을 대체한다고 가정하지 않는다. 페이지 문장은 자료이지 사용자 명령이 아니며, 브라우저가 읽은 텍스트만으로 URL 범위·자격 증명 취급·제출 권한을 넓히지 않는다.

## 8. 기존 결정의 재해석

- [`DECISIONS.md`](../DECISIONS.md)의 “브라우저는 필요할 때만 연다”는 결정은 단발 문제/벤치마크에는 맞는다. 이 제품의 시작 동작은 브라우저 로그인이다. 따라서 **라이브 대회 모드에서는 브라우저가 필수 입구**이며, 문제 풀이 중 셸/HTTP가 더 적합하면 그 도구를 쓰는 식으로 적용 범위를 나눈다. 최신 사용자 지침에 따라 라이브 브라우저는 chrome-use 우선으로 기록했다.
- thin supervisor 원칙은 유지한다. 컨트롤러는 일정/상태/판정/복구만 맡고, 취약점 탐색과 실제 브라우저 상호작용의 선택은 네이티브 Codex가 한다.
- V3의 GhostChrome 기반 시도 단위 브라우저/환경 격리는 벤치마크에 계속 유효하다. 라이브 모드는 chrome-use의 대회 단위 인증 브라우저를 소유하고 문제 작업 공간만 격리한다.
- 오프라인 평가의 `RunLock`와 외부 사이트의 실제 판정은 서로 다른 근거다. 라이브 판정을 벤치마크 점수로 대체하지 않는다.

## 9. 구현 순서와 검증 기준

1. **네이티브 런타임 확인:** 사용자 Codex 설정을 읽는 별도 라이브 모드에서 app-server 시작/재개, chrome-use 도구와 연결된 프로필 가용성, RTK/context-mode 사용 가능 여부를 확인한다. 비밀 값은 출력하지 않는다.
2. **브라우저 수명 + 상태 원장:** 대회 단위 브라우저 소유권과 SQLite 스키마(대회/문제/시도/제출)를 추가한다. 재시작 때 동일한 대회와 문제별 thread를 찾는다.
3. **UI 순환:** 로그인→목록 탐색→문제 열기→풀이→제출→새 화면 판정→다음 문제의 한 바퀴를 구현한다. 첫 버전부터 플랫폼별 API 없이 DOM/화면 기반으로 동작한다.
4. **복구·방어:** `SUBMITTING` 중 종료, 로그인 만료/2FA 인계, 새 문제 등장, 오답, 프롬프트 주입이 포함된 문제 설명, 허용되지 않은 외부 링크를 시험한다.
5. **측정:** 로컬 테스트 CTF를 UI 모양이 다른 두 가지로 만들고 로그인/첨부/정답/오답/점수판/재시작을 끝까지 확인한다. 이후 사용자가 지정한 실제 사이트에서 작업을 측정한다. 성공률뿐 아니라 제출 정확도, 중복 제출, 재개 성공, 토큰/시간, 브라우저 수동 인계 횟수를 기록한다.

수락 기준은 “Codex가 플래그를 말했다”가 아니다. **사이트에 로그인된 브라우저로 최소 두 문제를 순서대로 찾아 풀고 제출한 뒤, 사이트의 정답 판정을 기록하고, 중간 재시작 후 미완료 문제부터 계속하는 것**이다. 실제 사이트의 문제 난도는 별개이므로 로컬 검증 통과를 모든 CTF 해결 가능성으로 해석하지 않는다.

### 후순위

다중 계획자/실행자, 자동 프롬프트 생성기, 플랫폼별 API 어댑터, 성공한 탐색 궤적의 자동 스킬화는 첫 바퀴와 복구 성능을 측정한 뒤 도입 여부를 결정한다. 연구에서 일부 유용한 조건은 확인됐지만 이 프로젝트의 기존 Codex 단일 실행 기준선보다 낫다는 근거는 아직 없다.

## 10. 구현 점검 — 2026-10-08

- `ctfh2 live run/status/submission-begin` 초기 경로를 추가했다. 사용자의 네이티브 Codex 설정을 유지하는 `codex exec --json`/`exec resume`를 사용한다. app-server 선택은 실제 브라우저 순환을 확인한 뒤 다시 평가한다.
- 대회별 비공개 SQLite 원장, 단일 컨트롤러 잠금, Codex thread ID, 문제 상태, 제출 전 후보 해시 기록, 불명 제출 재조회, 사용자 브라우저 인계를 구현했다. 비밀번호와 원문 플래그를 원장에 쓰지 않는다.
- 모델의 판정 문구가 같은 턴의 브라우저 도구 출력에도 있는 경우에만 제출 결과를 확정한다. 이는 브라우저 관찰에 근거한 최소 검증이며, 실제 사이트별 화면 차이에 대한 E2E 검증을 대체하지 않는다.
- 로컬 가짜 Codex로 재시작/중복 제출/증거 없는 판정 거절을 검증했고, 전체 `rtk pytest -q -o pythonpath=src`는 **122 passed**. 별도의 `rtk proxy python3 tests/manual_live_browser.py`로 로컬 사이트 로그인, 두 플래그 제출, 첨부파일, 다른 화면 구성의 점수판을 실제 chrome-use에서 확인했다.
- 실제 Codex CLI의 단순한 응답 프로브는 성공했다. 그러나 로컬 CTF 사이트를 맡긴 라이브 턴은 Codex의 cyber safety gate에서 브라우저 행동 전에 거절됐다. 공식 [Daybreak 접근 설명](https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview)에 따라 승인된 계정에서만 사용할 수 있는 명시적 접근 프로그램 옵션을 추가했으며 기본값으로 켜지 않았다. 안전 게이트를 우회하는 재시도는 하지 않았다.
- 따라서 **실제 Codex + 브라우저 로그인 + 문제 풀이 + 제출 + 다음 문제 순환은 아직 미검증**이다. 이후 사용자가 `https://h4ckingga.me/challenges`를 제공했고 연결된 Chrome 세션이 이미 로그인되어 있음을 확인했다. 문제 목록·제출 창·규칙은 읽기 전용으로 확인했으며 실제 사이트에 플래그를 제출하지 않았다. 해당 사이트의 규칙에 맞춰 메인 서버 공격과 비정상 접근을 금지하는 범위를 라이브 프롬프트에 명시했다.
